# Argvia 组成与抽象边界

当前确定两个主要包：`@argvia/parser` 和 `@argvia/core`。宿主适配先确定职责隔离，发布位置通过实际运行入口评估。

## 参数解析

parser 接收已经分割、已确定作用范围的 argv 数组。它负责选项识别、值归属、值解析协议、默认值与重复处理，以及原始值、出现历史、显式提供状态和位置记录。

命令树、帮助与版本的产品含义、业务配置和进程状态由上层负责。命名位置参数的规则由 core 组织。

值解析可能参与参数绑定，例如贪婪追加根据候选值能否解析决定在哪里停止。后续组合接口必须保留这一点，并避免重复调用值回调。

parser 同时需要独立完整解析的使用方式，以及供 core 决定内建请求与执行约束的组合能力。准备结果与通过约束后的输入采用不同类型，尚未验证必填项时保留缺席可能。

## 命令核心

core 依赖 parser，组织命令和字段模型、命令路由、命名位置参数、帮助、版本、执行约束及类型化 handler 调用。

常规入口接收显式输入，保持可嵌入使用。配置文件读取、多来源合并及 Java 等领域规则由应用或后续配套能力承担。

归档中的 command 原型为命名参数、独立解析和来源信息提供研究依据，其能力归入 core 的统一规划。

## 宿主运行适配

argv、cwd、环境变量、真实 I/O、进程信号与退出状态属于宿主适配职责。

它的发布形式尚未确定。先通过真实入口评估是否需要独立依赖、支持范围或发布节奏，再比较应用组合、core 子入口和独立包。Node/Bun 的支持通过实际行为验证确定。

core 和 parser 的普通入口不读取进程全局，也不强制加载 Node 内建模块或 Node 类型。

## 语法与模块

值协议归 parser，命令与运行模型归 core。帮助、类型推导和运行行为共用同一份定义。

对象式、链式或其他语法形式通过使用场景比较；不同入口应复用同一模型和语义。内部模块依据职责组织，独立发布依据实际消费需求确定。

当前包只有空导出，以上描述为能力规划。输入策略、公共 API 与运行结果仍需逐项设计和验证。
