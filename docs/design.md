## 定位提案

> 面向 TypeScript 的 CLI 命令定义库，用一份定义驱动参数解析、运行时校验、帮助信息和处理函数类型。

目标使用者暂定为项目工具、脚手架、构建工具和 SDK 配套 CLI 的开发者。当前按 Node.js / TypeScript 库来推敲接口，具体运行平台、版本要求与发布方式仍待确定。

以下内容是设计验收目标，并非当前实现能力：

- 常见命令的处理函数无需手写输入类型或添加类型断言
- 默认值、必填规则和枚举候选能够决定处理函数获得的类型
- 拆分命令、抽出共享选项后，仍然保留类型信息
- 成功解析后的实际值与静态类型保持一致
- 参数规则、校验和帮助信息来自同一份定义

已选定单值选项的缺省规则：没有默认值且不要求必填时，省略输入得到 `undefined`，包括布尔选项。配置加载与合并由应用完成，最终默认值在合并后设置；无需参与配置合并的开关可显式声明 `{ default: false }`。第一轮运行实验仍保留原有布尔缺省行为，下一轮将同步这项选择。

需要通过相同使用场景与 Commander、citty 对照，判断 Argvia 能带来哪些具体改善，而不是只比较接口写法。

## 接口方向比较

| 方向 | 调用体验 | 主要取舍 |
| --- | --- | --- |
| 普通对象声明 | 参数规则集中，便于浏览和编辑 | 抽出对象后需要处理字面量类型丢失与关联约束 |
| 链式构建 | 每一步累积类型，便于组合转换规则 | 调用顺序与构建过程会成为调用者需要理解的契约 |
| 有序参数描述列表 | 位置顺序明确，描述可复用 | 选项按名称查找稍费眼，辅助函数较多 |

当前推荐候选是**声明式命令对象与类型化参数描述组合**：命令整体保持对象结构，参数构造函数负责保存类型信息；位置参数用数组表达顺序，选项用对象表达名称。该选择尚未定稿。

## 拟议用法

下列代码展示目标调用方式。`argvia` 是拟议包名，函数名称及导出尚未确定。

```ts
import { argument, defineCommand, option, runMain } from 'argvia'

const deploy = defineCommand({
  description: '部署应用',

  args: [
    argument.string('entry', { required: true }),
  ],

  options: {
    port: option.number({ default: 3000 }),
    mode: option.enum(['dev', 'prod'], { default: 'dev' }),
    token: option.string(),
  },

  async run({ args, options }) {
    await deployApplication({ entry: args.entry, ...options })
  },
})

const app = defineCommand({
  name: 'tool',
  commands: { deploy },
})

await runMain(app)
```

`deployApplication` 代表调用方提供的业务函数。文件、网络、认证等业务依赖可以通过处理函数的闭包接入。

对应的终端调用为：

```sh
tool deploy app.ts --port 3000 --mode prod
```

候选规则下，处理函数应获得以下类型：

| 字段 | 类型 |
| --- | --- |
| `args.entry` | `string` |
| `options.port` | `number` |
| `options.mode` | `'dev' \| 'prod'` |
| `options.token` | `string \| undefined` |

命令名暂由 `commands` 的键决定，根命令的 `name` 用于描述程序。叶子命令与分组命令是否共用 `defineCommand`，仍需要结合组合场景验证。

## 候选调用契约

以下规则用于讨论和验证，尚未作为稳定契约发布：

- `required: true` 表示必须显式输入，与默认值互斥
- 有默认值的字段消除 `undefined`，默认值仍接受校验
- 无默认值的可选单值字段保留 `undefined`，布尔字段遵循同一规则
- 枚举类型由候选集合决定，默认值不能扩大或缩小取值范围
- 位置参数按数组顺序匹配，可选位置参数之后不能出现必填位置参数
- 输入转换和校验通过后才调用处理函数
- 请求帮助时跳过必填输入检查，并且不调用处理函数
- 处理函数支持同步和异步，执行器等待异步处理完成
- 定义错误指出开发者的使用问题，输入错误向终端用户提供可操作的提示

定义阶段还需要考虑重复字段、别名冲突和空枚举等问题。第一轮可运行实验已为重复选项、未知选项、数值转换等选择了临时规则，详见 [接口实验记录](command-api-experiment.md)；稳定契约仍待确定。

## 执行接口提案

```ts
await run(app, { argv: ['deploy', 'app.ts'] })
await runMain(app)
```

`run` 接收明确的参数列表并返回结构化执行结果，适合测试和程序内调用。`runMain` 负责接入终端、输出诊断和设置退出码。两者使用同一份命令定义。

第一轮实验已尝试执行、帮助、输入错误三种结果，并区分业务异常传播与终端退出码，详见 [接口实验记录](command-api-experiment.md)。处理函数返回值的类型推导、输出接口和取消信号仍待设计。终端环境与测试环境确有替换需求时，再确定对应的 adapter。

解析、转换、校验、命令选择和帮助生成的复杂性应集中在库内。配置加载、日志与交互式提问暂作为调用方可组合的能力，其与执行上下文的关系需要由实际使用场景决定。

## 类型实验与验证范围

[typing.ts](prototypes/typing.ts) 保留此前的独立类型声明实验。它在 TypeScript 严格模式下验证了：

- 必填位置参数得到 `string`
- 可选位置参数得到 `string | undefined`
- 数值默认值产生 `number`，而非默认值字面量类型
- 枚举默认值保留完整联合类型
- 抽出的共享选项保留类型信息
- 未声明选项、错误默认值和不符合候选缺省规则的定义在编译期报错

在已提供 TypeScript 编译器的环境中，可以从仓库根目录检查：

```sh
tsc --strict --noEmit --lib ES2022 docs/prototypes/typing.ts
```

该声明实验使用 `const` 类型参数和 `NoInfer`，验证工具需支持这两项能力。它没有覆盖运行时行为；新的 [可运行实验](command-api-experiment.md) 补充了解析、校验、帮助、分组和执行结果验证。两者都不构成稳定公开接口。

第二组 [java-run 声明样例](prototypes/java-run-definition.ts) 验证已选定的单值缺省规则，以及字段拼写映射、重复数组、局部选项、透传上下文和默认命令键约束。它通过 `pnpm typecheck` 与第一组实验一起检查；其中的验证函数不会执行。完整业务请求、配置读取和命令选择仍需运行时验证。
